# 운영 검증 기록 — 2026-09-13

대상: https://www.yttm.kr

사용자가 운영 배포 완료를 알린 뒤 수행한 부분 스모크 검증이다. 초기에는 운영 배포 SHA와 Firebase 설정을 대조하지 않았으며, 이후 확인한 배포·설정 정보는 아래 별도 항목에 기록한다.

## 1차 확인 완료 — 조회 중심

- 쿠키 없는 HTTP 요청에서 `/`, `/login`, `/en/login`이 200으로 응답했다.
- 쿠키 없는 `/dashboard`, `/admin` 요청은 307과 `/ko/login` 위치로 응답했다.
- 비인증 관리자 사용자 API 요청은 403, YouTube 영상 정보·검색 API 요청은 401로 차단됐다. 관리자 API에는 실제 사용자 UID 대신 존재하지 않는 테스트 문자열을 사용했다.
- Chrome에 이미 로그인되어 있던 계정으로 `/login` 진입 시 대시보드로 이동했고, 기존 영상·컬렉션을 조회했다. 새 Google OAuth 로그인 성공을 검증한 것은 아니다.
- 같은 기존 세션에서 `/admin` 화면과 통계를 조회했다. 비관리자 로그인 계정의 접근 거부와 `ADMIN_UID` 환경변수 값 자체는 확인하지 않았다.
- 영상 추가 대화상자에서 `YouTube Developers iframe API`를 검색해 실제 결과 8개가 표시됐다. 추가 버튼은 누르지 않았다.
- 랜딩 페이지에 공개된 데모 공유 링크에서 영상과 타임라인이 표시됐다. 1:27 메모를 클릭한 후 실제 YouTube 영상 재생 및 이후 1:39 재생 시각을 확인했다. 프레임 단위 이동 정확도나 비로그인 브라우저에서의 공유 페이지 동작까지 검증한 것은 아니다.
- Chrome 뷰포트 412×839에서 대시보드의 문서 폭과 화면 폭이 모두 412px였다. 검사 후 뷰포트 설정을 복원했다. 모바일 실기기·Safari 검증은 아니다.
- `/robots.txt`, `/sitemap.xml`이 200으로 응답했고 sitemap 주소는 운영 도메인을 사용했다.

## 1차 변경 범위

기존 로그인 상태를 유지했다. 영상·메모·컬렉션 생성/수정/삭제, 계정 생성/이관, 지표 동의 변경, 권한·배포 설정 변경은 수행하지 않았다. 검색 요청으로 서버 호출 제한 카운터나 캐시가 갱신될 수 있다. 개인 식별 정보와 관리자 사용자 목록은 이 기록에 저장하지 않는다.

- 영상을 재생하고 현재 시각을 캡처해 0:07에 `[운영 검증 2026-09-13] 웹 저장·새로고침·확장 동기화 확인용 테스트 메모`를 저장했다.
- 새로고침 후 동일한 메모 본문·시각과 타임라인 1개 표시를 확인했다.

- 재로그인 후 같은 영상 페이지에서 동일한 메모를 확인했다.
- 설치된 Chrome 확장프로그램의 메모 사이드패널에서 같은 영상 제목과 0:07 테스트 메모가 표시됐다. 웹 → 설치된 확장프로그램 방향의 데이터 조회를 확인했다. 갱신 지연 시간까지 측정한 실시간 동기화 검증은 아니다.

### 2차 당시 미완료와 제약

- 확장 → 웹 역방향 저장은 확인하지 못했다. Chrome 창 전환 감지로 입력이 중단되었으며, 마지막 확인 화면에서는 확장 입력란이 비어 있고 저장 버튼이 비활성 상태였다. 이어서 네이티브 창 접근 오류가 발생했다.
- 동일 확장 화면을 별도 탭으로 열려는 시도도 브라우저 도구의 URL 정책에서 차단되어 중단했다. 제한을 우회하지 않았다. 이 도구 제약만으로 제품 결함이라고 판단하지 않는다.
- 이후 사용자가 직접 추가한 데이터로 역방향 반영을 확인했다. 아래 후속 검증을 참고한다.

## 후속 확인 — 기존 Google 계정 이관 시도에서 팝업 차단

사용자가 현재 로그인된 Google 계정으로 테스트하고 데이터를 합쳐도 된다고 승인했다. 인앱 브라우저와 Chrome은 Google 로그인 세션을 공유하지 않으므로 Chrome에서 기존 웹 계정을 로그아웃하고 새 운영 게스트 세션을 시작했다. 앞서 만든 인앱 브라우저의 빈 게스트와는 별개다.

- 새 게스트 영상: `/videos/NQvTo0Ueh861DB2Wabkq` (YouTube `M7lc1UVf-VE`).
- 새 게스트 메모 1개: 0:00, `[계정 이관 검증 2026-09-13] 게스트에서 작성 — 기존 Google 계정 연결 후 보존 확인`.
- 계정 연결 전 새로고침으로 게스트 배지와 영상·메모의 저장 유지를 확인했다.
- `Google로 계정 연결` 클릭 후 브라우저 콘솔에서 `계정 연결 실패: FirebaseError: Firebase: Error (auth/popup-blocked).`가 기록됐다.
- 화면에는 오류 안내가 표시되지 않았고, 새로고침 후에도 게스트 배지·연결 버튼과 동일한 테스트 메모가 유지됐다. 이관 성공으로 계산하지 않는다.
- 수정 전 소스는 `auth/credential-already-in-use` 처리 중 두 번째 `signInWithPopup`을 호출했다 (`src/lib/firebase/auth.ts`). 이 비동기 재팝업 경로가 원인 후보이나, 이번 관찰만으로 첫 번째와 두 번째 팝업 중 어느 호출이 차단됐는지는 확정하지 않는다.
- 수정 전 `UserMenu`는 연결 실패를 콘솔에만 출력해 사용자에게 실패·재시도 안내를 제공하지 않았다.

데이터 접근을 유지하기 위해 Chrome의 새 게스트 세션에서 로그아웃하지 않았다. 기존 Google 계정의 데이터는 삭제·수정하지 않았으며 이관 완료도 확인되지 않았다. 새 게스트 영상·메모와 두 브라우저의 게스트 세션을 유지했다. 기존 Google 계정으로 웹 로그인 상태를 복원하지 않은 상태임에 유의한다. 팝업 차단 설정을 변경하거나 브라우저 제한을 우회하지 않았다.

## 로컬 수정 — 재팝업 제거와 실패 복구 (배포 전 기록)

- 기존 Google 계정과 충돌하면 `GoogleAuthProvider.credentialFromError`에서 받은 자격증명으로 `signInWithCredential`을 호출한다. 비동기 두 번째 팝업은 제거했다. 새 Google 계정 연결은 기존 `linkWithPopup` 경로를 유지한다.
- 서버가 익명 세션 쿠키로 이관 원본을 결정하는 권한 검증은 변경하지 않았다. 데이터 이관 성공 후에만 Google 서버 세션을 생성한다.
- 이관 실패 시에는 이관부터, 이관 후 세션 갱신 실패 시에는 세션 갱신부터 재시도한다. 새로고침 뒤 Firebase 인증 상태 복원을 기다리는 처리도 포함했다. 클라이언트 진행 상태에 OAuth 자격증명은 저장하지 않는다.
- 연결 중 중복 클릭과 로그아웃을 막고, 팝업 차단·취소·네트워크 오류·기타 실패에 대한 한국어/영어 대화상자와 재시도 버튼을 추가했다. Firebase 오류 전체를 콘솔에 출력하지 않는다.
- 인증 제어 흐름과 오류 분류는 단위 테스트로 검사한다. 격리 브라우저 테스트는 Google API 로더를 차단해 실제 실패 안내·재시도·닫기·게스트 쿠키 유지 및 이관/세션 API 미호출을 검사한다. 실제 Google OAuth 성공이나 운영 데이터 이관을 대신하는 테스트가 아니다.

구현 근거: [Firebase GoogleAuthProvider API](https://firebase.google.com/docs/reference/js/auth.googleauthprovider), [Firebase 계정 연결 안내](https://firebase.google.com/docs/auth/web/account-linking).

## 후속 확인 — 일반 Google 계정의 운영 권한 차단

- 사용자가 지정한 비관리자 Google 계정을 별도 Chrome `Minu` 프로필에서 사용했다. Google 계정 표시와 YTTM의 `Minu Song` 이름 및 빈 대시보드를 확인했다. 기존 관리자 프로필은 관리자 로그인 상태로 유지했다.

## 후속 확인 — 운영 규칙 불일치 및 환경 설정

### 배포된 Firestore 규칙: 조치 필요

Firebase CLI의 기존 로그인으로 Rules API의 release 목록과 ruleset 소스만 조회했다. 운영 데이터 조회·쓰기나 규칙 배포는 수행하지 않았다.

- 대상 프로젝트: `yttm-38af5`, release: `projects/yttm-38af5/releases/cloud.firestore`.
- 활성 ruleset: `13b4f99b-627a-42b3-af95-fb5212e18703`.
- release 갱신 시각: `2026-03-28T14:36:09.496042Z`.
- 운영 소스 SHA-256: `13100e70769269f108f4b17b9e323147f09cd25e0a7f39752a54ef0e40c34ce4`.
- 저장소 `firestore.rules` SHA-256: `7bb61dd5294aa9510b17650b57d44b5de6a739ee958d21ad6fe3808d93f9c67e`.
- 줄바꿈과 앞뒤 공백을 정규화해도 서로 다르다. 운영 규칙에는 저장소의 보안 강화가 반영되지 않았다.

운영 소스에서 확인한 차이:

1. `shareToken != null`인 영상과 하위 메모는 비인증 직접 읽기를 허용한다. 토큰을 제출하거나 알고 있는지 검사하지 않는다. 저장소 규칙은 공유 여부와 관계없이 직접 읽기를 소유자에게만 허용한다.
2. 영상·컬렉션의 기존 소유자는 `userId`를 다른 UID로 수정할 수 있다. 저장소 규칙은 업데이트 전후 소유자 UID가 같아야 한다.
3. 사용자 프로필 생성·수정에서 본문 `uid`의 일치·불변 조건이 없다. 저장소 규칙에는 해당 조건이 있다.

이는 활성 규칙 소스의 권한 분석이며, 운영 데이터로 무단 접근·소유자 변경을 재현하거나 실제 유출을 확인한 결과는 아니다. 기존 웹의 비공개 영상 404 확인만으로 Firestore 클라이언트 접근까지 안전하다고 판단할 수 없다.

웹 배포와 Firestore 규칙 배포는 별도다. [Firebase 규칙 배포 안내](https://firebase.google.com/docs/rules/manage-deploy)

### Vercel 환경 설정: 조회 완료

- Vercel의 YTTM Production 화면은 `main`의 `cceae347f00c12f141c57da6448a9a10585c0a79`를 Ready로 표시했다. 배포 ID는 `EZvMbNuaMVFDAsEPb8QJ9kEK9qr7`이다. 이후 develop의 `5428222` [CI 실행](https://github.com/smw0807/yttm/actions/runs/34742165228)도 성공했다. CI 성공을 운영 반영으로 계산하지 않는다.
- `ADMIN_UID`는 Production 범위의 Secret으로 등록돼 있다. Firebase 공개 설정 6개, `FIREBASE_ADMIN_SDK`, `YOUTUBE_API_KEY`, `NEXT_PUBLIC_BASE_URL`은 All Environments에 등록돼 있다.
- 공개 설정인 `NEXT_PUBLIC_BASE_URL=https://www.yttm.kr`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID=yttm-38af5`를 확인했다. 비밀값은 공개·복사하지 않았으며, 마스킹된 값의 내용이나 현 배포에 주입된 값 전체까지 검증한 것은 아니다.

- 환경변수나 배포 설정은 변경하지 않았다.

### 운영 규칙 배포 준비 — 승인 후 실행

에뮬레이터 설정과 분리한 `firebase.production.json`을 추가했다. 프로젝트와 배포 대상을 명시해 **규칙만** 배포하며 웹·인덱스·데이터는 배포 대상에 포함하지 않는다. 아래 명령은 아직 실행하지 않았다.

```sh
yarn firebase deploy --only firestore:rules --project yttm-38af5 --config firebase.production.json
```

배포 승인 후 확인 순서:

1. 배포 직전에 활성 ruleset을 재확인하고 현재 소스와 release 식별자를 보관한다.
2. 규칙만 배포한 뒤 활성 release의 소스가 저장소와 일치하는지 재조회한다. 전파 지연을 고려한다.
3. 로그인한 소유자의 영상·메모·컬렉션 조회와 확장 조회, 비인증 공유 링크 표시를 확인한다.
4. 테스트용 데이터 생성·정리가 승인된 범위에서 다른 계정의 직접 SDK 접근 차단 및 소유자 변경 거부를 확인한다. Admin SDK는 규칙을 우회하므로 이 검증의 클라이언트로 사용하지 않는다.
5. 정상 사용자 경로가 차단된다면 원인을 확인한다. 보안이 약한 이전 규칙으로 자동 롤백하지 않고 영향과 대응을 사용자에게 보고한다.
